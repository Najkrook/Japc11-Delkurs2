Sushi audit: independent verification

27 October 2026 · Local checkout 5ee6972833e931ec7b23f7588026cfa621b6c914

The report identifies real presentation regressions. Its strongest evidence concerns misleading money displays, hidden production information, and artwork that does not reflect ownership. Its balance and educational conclusions mix documented design choices with defects.

Scope: compared the original report against current source, the introducing Git diff, the product brief, the GDD, and the balance model. Reproduced the empty-register bug in the local browser and exercised actual render, collection, and purchase code with a frozen clock. No game implementation, economy values, or original report were changed.

Rates must first be unlocked and purchased, collection caps can stop income, and purchases remain medal-gated. Cash may outpace weekly unlocks, but the asserted semester timeline needs a study/collection schedule. No explicit gameplay wallet maximum was found.

The report correctly recognizes that ignoring client-supplied grants is intended. Local checks cannot establish production synchronization correctness.

Origin and test gap

The diff for 5ee6972 introduces the ¥6,280 fallback, synthetic statistics, hidden production containers, static date/time, icon mappings, and raster scene. Its message explicitly mentions retaining screen-reader telemetry and test contracts. The code supports a regression caused by matching the illustration; it does not establish malicious intent.

The ¥18,740 wallet and ¥6,280 pending-income seed is restricted to the localhost service, the local-dev-user account, and an empty balance/register/inventory (service.ts:114–131). Default restaurant state remains zero/zero. The visible fallback, unlike that seed, applies to every authenticated game view.

The selected existing view, economy, purchase, and scene suites pass 87/87. Their template/string/marker checks do not prove that data is visible or that removing a decoration removes its pixels. The new diagnostic produces four failing UI checks out of five, with the nonzero amount serving as a passing control. This is evidence of a coverage gap, not a claim that all repository tests pass.

Recommended repair order

  1. Make the money display truthful at zero and positive balances; replace or remove unsupported daily statistics and static clock/calendar.
  2. Restore visible rate, cap, progress, full-register warning, and bottleneck guidance with a responsive layout. Removing sr-only alone needs layout verification.
  3. Make purchased/placed objects actual removable layers. Assess the prior vector scene as a recovery option; a blanket commit revert would also undo unrelated presentation work.
  4. Correct icon actions and language consistency. Add rendered-browser coverage for zero/nonzero money, cap visibility, and visual ownership/placement differences.
  5. Evaluate economy pacing separately using an explicit medal-unlock and collection schedule. Preserve current intended bottleneck and cosmetic behavior until a design change is chosen.
